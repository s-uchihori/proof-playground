## 背景（事実）

- TLA+ も Lean も知らない — 依頼文（「どちらも知らない人向け」）

依頼文から分かることは、これだけ。以下はすべて推測。

## 背景（推測）

- Web のバックエンドやアプリを書くエンジニア。
  理由: このリポジトリの TLA+ の例が、更新の消失・デッドロック・在庫の引き当てという、Web のバックエンドでよく出る題材だから。
- 高校数学（数列、数学的帰納法、二次式の展開、三平方の定理、背理法）は分かる。
  理由: リポジトリの README がこの範囲を想定読者にしているから。
- チームのナレッジとして後から読み返す。1本に使える時間は 10〜15 分。
  理由: 依頼の置き場所が「チームのナレッジ文書」であることからの推測。

## この分野で既に知っていること（推測）

- SQL の `SELECT` / `UPDATE`、トランザクション、行ロックの言葉は知っている。更新の消失やデッドロックを、言葉か障害としては見たことがある。
- 単体テスト、型チェック、CI の「緑」は日常的に見ている。
- 数学的帰納法と三平方の定理の、高校での証明の形は覚えている（細部は忘れているかもしれない）。
- 「形式手法」「モデル検査」「定理証明」という言葉は聞いたことがあるかもしれないが、使ったことはない。

## 怪しいところ（推測。資料の芯にする）

- 「検査が通った（緑）」を、テストの緑と同じ重さで受け取りやすい。
  - TLC の `No error has been found` は「設定した大きさの模型では、どの順番でも壊れなかった」であって、「実装が正しい」でも「何人でも大丈夫」でもない。
  - Lean のビルドが通ったことは「書いた前提と定義のもとで、書いた命題が正しい」であって、「定義が現実を正しく写している」までは言っていない。
- TLA+ と Lean を「どちらも形式手法」と一括りにして、使い分けを判定できない。
- TLC の反例の出力（`State 1` 〜）や Lean のエラー（`⊢` の行）を見ても、どこを読めばよいか分からない。
- 「自分の設計のどこに TLA+ を当てるか」の勘所が無い（何でも検査できると思うか、何にも使えないと思うか）。

## 読み方（推測）

- 日本語。1段落は短く。コードと実際の出力が先にあり、言葉で読み方を添える形を好む（エンジニアなので）。
- 1本 10〜15 分。演習はしない。手元で走らせるのは任意。

## この資料で省くもの

- 道具のインストール手順（リポジトリの README にある）
- TLA+ の文法の網羅、Lean のタクティクの網羅
- 形式手法の歴史や一般論
- SQL・ロック・CI など、バックエンドの基礎用語の説明

## 未確認（本人に聞くこと）
